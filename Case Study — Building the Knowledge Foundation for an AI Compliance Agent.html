Teaching an AI agent to answer like a compliance expert

One

Investigators were searching a haystack, not a library

Suspicious-activity investigators need fast, correct answers to procedural questions in the middle of live casework — which typology applies, what a filing requires, what a jurisdiction-specific step looks like.

The tool they had was open enterprise search, scoped to everything a logged-in employee could see. That included final approved procedures, but also working drafts under track changes, procedures awaiting approval, superseded versions, stakeholder review copies, and material outside the team's scope entirely — all returned side by side, with no way to tell them apart.

Acting on the wrong result carried real consequences: a missed filing requirement, a step that had since changed, a write-up that failed QC. And when investigators didn't trust what search gave them, they escalated — asking a pod lead, manager, or subject-matter expert instead. Across a population of roughly 200 investigators, that added up to a steady, avoidable tax on the team's most senior capacity.

Two

My mandate: build the knowledge foundation, not the chatbot

Engineering could stand up an AI agent and connect it to a search platform and a language model in days. The harder, slower problem was mine: deciding exactly what that agent was allowed to know, how it was allowed to speak, and how that would stay true over time.

I led the project end to end from the content and governance side, working alongside platform engineering and compliance subject-matter experts. My scope broke into three pillars:

  • Content architecture — deciding what a trustworthy, curated source of truth looks like, and building it.
  • Governance model — the rules for what enters and leaves that source, and how it's kept current.
  • Behavioral guardrails & QA framework — defining what a "correct" answer means precisely enough to test it.
Three

Designing the knowledge architecture

The fix wasn't a better search algorithm — it was narrowing what the agent was ever allowed to see.

I scoped and curated a single collection of 82 approved procedures covering the full investigative workflow, from initial alert review through post-investigation actions, and explicitly excluded adjacent content that didn't belong in an operational answer. I tagged every document by jurisdiction so the agent could serve only jurisdiction-appropriate guidance once an investigator's jurisdiction was confirmed.

I also wrote the ongoing content lifecycle every future update has to follow: revise under change control → approve through the standard review process → accept changes and replace the source file → allow the search index to refresh → validate the agent actually retrieves the new version → log completion. Nothing enters the agent's world without going through that loop — new documents specifically require a manual step into the collection, so nothing arrives silently.

Four

Under the hood: the retrieval architecture

This is a retrieval-augmented setup, not a fine-tuned model — the agent knows nothing on its own. Every answer is grounded in a document it retrieved at the moment of the question, which is precisely why the retrieval layer was worth designing this carefully.

  • Model — Claude Sonnet 5, used purely as a reasoning and response layer. It never answers from its own training data on procedural questions; it's instructed to answer only from what it retrieves.
  • Retrieval integration — the agent platform connects to the enterprise search index through a Model Context Protocol (MCP) integration, scoped at query time to the one ringfenced collection I built. It has no path to the organization's broader search index at all — the boundary is structural, not just a prompt instruction.
  • Indexing cadence — documents already in the collection are reindexed daily so edits to approved procedures propagate automatically. New documents don't: they require a deliberate two-step add — into the source folder, then manually into the collection — a gap I designed on purpose so nothing enters the agent's knowledge silently.
  • Behavioral contract, decoupled from retrieval — the guardrails, citation rules, jurisdiction logic, and disclaimers live in a separately versioned context file I own, not hardcoded into the retrieval pipeline. That split meant I could tighten the agent's behavior without touching what it's allowed to retrieve, and vice versa.
  • Two access surfaces, one behavior — an in-platform agent portal and a dedicated team-chat channel both call the same backend, the same collection, and the same context file, so there's no separate rules to maintain per channel.
  • Observability — execution metadata (who ran it, what ran, duration, status) is logged separately from response content, since responses can touch sensitive case-adjacent language; a dedicated LLM-observability tool captures full reasoning traces and tool calls for QA review, with conversation threads retained for 90 days.
Five

Defining what "correct" means

An agent with the right sources can still answer badly. I authored the behavioral contract that governs how it's allowed to respond, then built the rubric to test it against.

Hard stop on personal dataAny customer identifier in a message triggers an immediate refusal and a delete instruction — no exceptions.
No case decisionsThe agent will not tell an investigator whether to file, clear, or escalate a case, or draft filing narratives.
Cites its sourceEvery substantive answer points back to the original approved article, never asserted without attribution.
Escalates its own uncertaintyWhen guidance isn't in scope, it says so and routes the investigator to the right human channel.
Standing disclaimerEvery answer states it's advisory and the investigator owns validation — with an enhanced warning on high-risk topics like filing guidance.
Jurisdiction confirmationThe agent confirms jurisdiction before giving jurisdiction-dependent guidance, every conversation.

From that contract, I built a QA rubric scoring every test response across six dimensions: accuracy, source citation, jurisdiction handling, guardrail compliance, tone, and disclaimer/analyst-validation. A response only passes if it clears all six — a correct answer with a missing disclaimer still fails. That rubric became the shared pass/fail language for engineering, compliance, and me for the rest of the project.

Rollout, testing, and staying honest about the results

I designed a two-phase rollout — domestic investigators first, international second — with each phase required to independently clear the same bar. Results from Phase 1 don't get to count as evidence for Phase 2; the second phase has to earn it on its own.

Go-live bar: 95%

First-pass Phase 1 result was 85.3% (29/34) — below threshold, so it blocked go-live rather than being waved through. After remediating the agent's behavioral contract against every failed dimension, the second full test round cleared the bar.

Live in production · US and international

I also defined the rollback plan before launch: a fixed set of triggers — a guardrail failure, a personal-data exposure, a missing disclaimer at scale — that disable the agent immediately, with investigators redirected to the knowledge portal and their pod lead. No platform changes required, phase-level or global depending on the trigger. Deciding how to fail safely was as much a part of the design as deciding how to succeed.

Eight

What I'd carry forward

Three things I'd repeat on the next AI knowledge project without hesitation.

  • Treat the agent's knowledge base like any other regulated content library — named ownership, version control, and a lifecycle process, not a folder someone remembers to update.
  • Guardrails are a governance artifact, not a prompt tweak. They only mean something once they're written down, testable, and auditable against a rubric.
  • Design the measurement before launch. Setting the 95% bar and the six-dimension rubric up front is the only reason the 85% result was a checkpoint instead of a surprise.
