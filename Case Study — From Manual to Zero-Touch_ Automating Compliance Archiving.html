One

A small task, repeated until it wasn't small anymore

Every time a compliance procedure changed, the previous version couldn't just vanish — it had to be preserved: dated, version-numbered, published, and made findable, before anyone could trust the new version was live.

That happened roughly fifty times a month. And every one of those fifty times, it was the same person doing the same handful of steps by hand: pull the outgoing article, save it as a PDF, open the content platform, create a new record with the correct version number and date range typed in manually, publish it, then go update the archive index itself to include it.

Five minutes doesn't sound like much on its own. But fifty times a month, every month, it became a standing tax on attention — and every manual step was a place a version number or a date format could quietly slip.

The task itself was never complicated. It was just relentless — and relentless is exactly what automation is for.

Two

Designed and built solo, start to finish

I owned this project end to end — no engineering team, no handoff. Every layer of it is mine.

  • The process logic — the versioning rules, the date-range math, the naming conventions that keep fifty records a month consistent with each other.
  • The automation itself — built in n8n, node by node, from the trigger through to publishing.
  • The resilience design — a manual fallback path so the process worked on day one, before every dependency was in place.
  • The documentation — step-by-step instructions and a troubleshooting reference, so the workflow doesn't depend on me to keep running.
  • The access and coordination work — credentialing, integration approvals, and the cross-team requests needed to close the gaps I couldn't close alone.

I didn't wait for every piece to be perfect before shipping something useful. I launched with the manual path running alongside the automated one, then closed each remaining gap myself over time — until there was nothing left for a person to do at all.

Four

Under the hood: how it's actually built

This is an n8n workflow, built and maintained by me directly in the node editor — not a low-code template, and not handed off to engineering to implement.

  • Trigger layer — a webhook fires automatically when a release is published in the CMS. A conditional node inspects the release name and only continues if it matches the pattern for a real procedure update, filtering out minor edits and typo fixes.
  • Read & calculate — the workflow calls the CMS's content API to read the existing archive index and the most recent version's end date. A JavaScript expression node counts existing entries to derive the next version number, then computes the new start and end dates from the last recorded date, with strict handling of the date format so downstream steps never misparse it.
  • Write & publish — the workflow calls the CMS API to create a new versioned record with the calculated title, version number, and file reference, then publishes it. A second API call rebuilds the archive index's content array with the new record prepended, and republishes the index itself.
  • State & idempotency — a final node writes a processed flag back to the source, so the same release can never be picked up and re-run twice.

Authentication runs through separate credentials scoped to each system the workflow touches, and every node is documented inline so the logic is legible to someone who didn't build it — which mattered, since for a stretch of this project a manual fallback path had to run in parallel with the automation while two integrations were still pending approval.

Five

Built to keep running without me

A workflow that only works when you're watching it isn't automation — it's a chore with extra steps. I designed this one to be someone else's tool, not just mine.

Fallback path from day oneLaunched with a manual backup route alongside the automated one, so the process never blocked on a pending integration.
Documented failure modesA troubleshooting reference maps each known error to its likely cause and its fix, so anyone — not just me — can resolve it.
Self-cleaning by designProcessed records are marked automatically, so the workflow never reprocesses the same update twice.
Filtered triggersThe workflow recognizes what counts as a real release versus a minor edit, so it only runs when it should.
